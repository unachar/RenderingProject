## 目的と採用基準

ユーザー指定の順序でGPU余力を確保し、30%入力のTSRを安定させ、最後に残存ボトルネックへ構造的対策を行う。パス単体の短縮では採用しない。CPU/GPUフレーム時間、1% Low、画質、ちらつき、残像を同じ条件で比較する。各変更は独立した設定で旧経路へ戻せるようにする。

## 初回調査で確認したこと

- C++ / DirectX 12プロジェクト。Unityではない。
- `source/rendering/renderprofiler.h` はFrame単独のGPU時間とパス別時間を持つ。現状のPassTiming/GpuEventには親識別子がなく、親子パスの合算を避ける契約を明確にする必要がある。
- `source/rendering/rayreflections.cpp` は反射とGIを実行し、個別の履歴有効状態とNRDチェッカーボード設定を持つ。GIのイベント名はTrace and Filterであり、分離する余地がある。
- `source/rendering/raytracing.cpp` はBLASにALLOW_UPDATE / PERFORM_UPDATEを使用する経路を持つ。P2では新規実装前に更新条件と既存再利用を確認する。
- `source/rendering/postprocesspass.cpp` に既存TAA・アップスケール処理とAdvancedEffectsへの接続がある。フォグ・DOF等の実際の解像度は追加調査対象とする。
- 追加確認: `raytracing.cpp`の`DXR Reflections`イベントはGIも含む`RayReflections::Execute`全体を囲む。P1-1では親を反射専用時間として扱わず、反射/GIの子区間を分ける。単なるイベント名追加では帰属の誤りを解消できない。
- 追加確認: `advancedeffects.h`のDual Bloomは既に半解像度を起点とするmipチェーンを持つ。Froxel Fogはタイル化した3Dグリッドで計算する。これらを「未対応」として再度低解像度化しない。
- 同ファイルのDOFは全画面のPost Aに対して`groupsX/groupsY`でdispatchする。P1-4の具体的な調査対象とし、CoCと前景/背景の境界を保つ縮小・復元が必要。Motion Blurの評価内容はResolveシェーダーを確認してから判断する。
- 現在の作業ツリーを再確認したところ、既存の`render_bundle.txt`変更はなく、未追跡の本設計案のみだった。開始時点の状態を現在の変更として扱わない。
- `scripts/validate-rendering.ps1`、`scripts/validate-gi.ps1`、`scripts/validate-play-rendering.ps1` にGPU検証経路がある。
- `docs/deferred-rendering-performance.md` の過去計測ではGPU短縮とCPU/フレーム時間悪化が併記されている。過去の短期計測を今回の採用証拠として再利用しない。
- 開始時点で`render_bundle.txt`に既存変更がある。今回の変更へ混ぜない。

## 実装方式の比較

1. 既存プロファイラーと検証シーンを拡張する方式を推奨する。通常描画と同じ経路を検証でき、初期変更も小さい。
2. 独立したベンチマーク専用アプリは条件を隔離しやすいが、通常描画との乖離と保守費用が増える。
3. 全基盤を一括置換する方式は切り分けと旧経路比較が難しいため採用しない。

## 最初の実装単位: 固定比較と履歴安全性

### 固定比較

シーン、シード、カメラ経路、アニメーション/物理ステップ、出力/内部解像度、品質設定、露光条件をマニフェストに保存する。比較対象以外の設定差を検出したら比較を不成立とする。通常ユーザー設定を永続変更しない。

初期の測定規約はウォームアップ120フレーム、測定600フレーム、A/BとB/Aを含む複数回とする。速度に応じて実時間ではなく同じシミュレーション時刻を再生する。VSyncとFPS上限、ビルド構成、GPU/ドライバー、計測機能の有無を記録する。

フレームSerialで遅延GPU結果とCPU/レイ数/履歴統計を対応付ける。欠落GPU結果を0msとして平均しない。1% Lowは測定区間の遅い1%のフレーム時間の平均の逆数として定義し、平均FPSと区別する。VRAMはアダプターの使用量/予算とアプリの管理する割当量を区別する。

### 計測

FrameのGPU区間をフレーム全体の基準とする。親イベントはinclusiveとして表示し、親識別子と深さを記録する。子を差し引くexclusive値は同一キュー上の包含区間にだけ使用し、並列キューの時間を単純に合算しない。

反射をTrace / Denoise / Composeに分ける。GIも同様に分類する。CPU/GPUフレーム時間、パス時間、有効サンプル数、1% Low、VRAM、実行レイ数をCSV/JSONへ出す。レイ数は推定dispatch画素数と実際のTraceRay呼び出し数を区別する。

履歴棄却率は対象機能別に定義する。独自再投影では対象画素数と棄却画素数を数え、リセット理由と併記する。NRD内部棄却率を取得できない場合は未取得とし、アプリの全体リセット率で代用したと誤記しない。追加readbackは非同期リングで回収する。

### 共通履歴契約

カメラID、カメラカット、入出力サイズ、シーン世代、照明世代、露光、Stable ID/LOD世代、フレーム連続性を入力に、理由ビットと機能別の履歴利用可否を返す。初期版は安全側の全体リセットから始め、局所無効化は信頼できる画素対応がある機能に限定する。

| 変化 | 初期版の扱い |
| --- | --- |
| 初回、フレーム欠落、カメラ切替/カット | 対象機能の履歴を破棄 |
| 出力/内部解像度の変更 | サイズ依存リソースを再確保し履歴を破棄 |
| シーン切替/形状変更/LOD変更 | 影響機能を無効化。画素対応がなければ全体リセット |
| 照明/発光の変更 | GI/反射の照明履歴を無効化。TSRはReactive情報が不十分ならリセット |
| 露光変更 | 履歴の色空間と露光比による補正を実装した経路のみ継続、それ以外は破棄 |
| 機能/デノイザー/入力形式の切替 | 切替先の履歴を無効化 |

通常のカメラ移動を毎フレームの全リセットにしない。VelocityはUV/画素単位、現在→前フレームの方向、ジッターの扱いを既存シェーダーから確認して文書化する。

### 検証

親子イベント集計、欠落タイムスタンプ、1% Low、履歴理由の単体検証を行う。固定再生の反復でマニフェストとシーン状態が一致することを確認する。既存の描画/GI検証を使い、履歴切替・リサイズ・照明編集の回帰とD3D12エラーを検査する。Releaseで性能、Debugで状態検証を行い、計測機能自体の費用も比較する。

## 後続フェーズ

P1-2: 粗さ・寄与・動き・深度エッジを分類してデバッグ表示する。任意の疎密サンプルをNRDチェッカーボードとして渡さない。密な信号への復元または対応する入力契約を先に検証する。

P1-3: GIの安定領域を間引き、遮蔽解除・移動・照明編集を優先する。未更新画素にも再投影した有効履歴、信頼度、経過フレームを保持する。無効履歴を未更新として放置しない。

P1-4/5: AdvancedEffectsを含む解像度と処理順を棚卸しする。未対応箇所だけ低解像度化し、同じ段階/解像度の合成だけ統合する。露光・トーンマップ・シャープニングの順序を保存する。

P2: Transform/Geometry/Material/追加削除を分離し、ASの再利用/UPDATE/REBUILDを選ぶ。DXR仕様上のUPDATE条件に適合しない変更はREBUILDする。共通DXR LODとProxy BLASを使い、画面外寄与を保つ。GPU時間を平滑化した予算と差分転送を追加する。Static/Dynamic AS分割は計測後に判断する。

P3: 共通履歴契約とVelocity確認後、出力解像度履歴への再構成、深度/画面外/遮蔽解除棄却、細線/発光/半透明の安定化、Stable ID/LOD連携を順に入れる。Performance/Balanced/Qualityを設け、30%入力でNIS+TAAと比較する。TSR選択時はTAA/NISを重複実行しない。Resurrection、出力超過履歴、高度なLOD間ReSTIR再利用は初期版に含めない。

P4: P1–P3の実測で必要性を確認してから、GPU Driven Visibility Buffer、面内評価共有、寿命に基づくAlias、RenderGraphのQueue/Fence管理、永続PSO/Shaderキャッシュへ進む。輪郭/深度/Velocityを保護し、GPUタイムラインの実際の並列区間を検証する。VRAM、平均性能、スパイク改善を別々に報告する。

## フェーズの判定

鏡面、夜景ネオン、移動物体、遮蔽解除、急な照明変更、細線、遠景で比較画像と時間的変動を記録する。静止シーンでは不要なAS構築/転送0、動的シーンでは生成削除/アニメーション/LOD反映を検証する。効果の再現性や画質が不足する機能は無効のまま残す。

目標フレーム時間と画質の数値閾値はユーザーから未指定。比較測定と成果物の作成は進められるが、絶対目標達成や全フェーズ完了とは宣言しない。
