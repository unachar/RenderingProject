# `.noise` マテリアル

プロシージャルスタジオのテクスチャ設定を、画素ではなくバージョン付き JSON の `.noise` ファイルに保存する。マテリアルでは UV 座標で GPU の計算式を直接評価するため、PNG/DDS の保存解像度や圧縮率には依存しない。浮動小数点精度・画面の画素数・微分幅による限界はある。

## 使い方

1. プロシージャルスタジオのテクスチャ画面で模様を調整する。
2. 「.noise を保存...」からプロジェクトの `asset` フォルダ内に保存する。
3. アセットブラウザーからマテリアルの `Base Color`、`Normal`、`Height (POM)` にドロップする。
4. マテリアルを保存する。各入力欄には通常の画像も引き続き指定できる。例えば Base Color は PNG、Normal と Height は `.noise` にできる。1 つの欄ではいずれか一方を使う。

| 入力欄 | `.noise` の評価 |
| --- | --- |
| Base Color | スタジオの色設定を含むカラー |
| Normal | スカラー場の UV 勾配から接空間法線を生成。スタジオの法線強度とマテリアルの Strength を使用 |
| Height (POM) | スカラー場の高さ。既存の Parallax Depth / Steps、深度オフセット、セルフシャドウと共用 |

出力の Color / Height / Normal 選択はスタジオの画像プレビュー・画像保存用。`.noise` をどの欄に置いたかでマテリアル側の解釈が決まる。高さは白が上面、黒が奥。POM は既存と同じく不透明マテリアル専用で、Depth が 0 なら無効。

`.noise を読み込む...` で設定を復元できる。時間は保存時点の値で固定し、マテリアル側で自動再生はしない。再保存後のアセット更新で参照中のマテリアルを更新する。ファイル移動は通常のアセット操作で行い、`.meta` の GUID を保持する。

22 種類の基底ノイズ、フラクタル合成、レンガや幾何学模様など既存の GPU 生成対象に対応する。倍精度 CPU 計算を使う Mandelbrot / Julia の `.noise` 保存は無効にし、従来の画像保存を残している。未対応の式へ黙って置き換えない。

## 実装と検証

- 定義: `source/assets/noiseasset.*`。壊れた JSON・不正な列挙値・非有限数・過大な値・未対応の版を拒否し、読み込み失敗時は呼び出し元の設定を保持する。
- 共通評価: `shader/hlsl/ProceduralTexture.hlsli`。スタジオの GPU 画像出力も同じスカラー・カラー関数を使う。
- GPU パラメーター: 1 入力 208 バイト、3 入力で 624 バイト。既存 PBR 定数の先頭オフセットを保持して末尾に追加。マテリアル定数は 3040 バイト、GPU Scene レコードは 3136 バイト。
- 通常画像には従来の TextureManager を使う。`.noise` はテクスチャデスクリプターを消費しない。マテリアル・アセットのプレビュー、GPU 駆動描画、反射・GI カードの色にも定義を引き渡す。
- 通常画像のサンプリングより計算量が増える。特に高オクターブのノイズを POM に指定すると、レイの各ステップでノイズ計算が発生する。

### Voronoi の負荷対策

Voronoi 基底は、まず現在のセルの特徴点を求め、その距離より近くなり得ないセルを探索から除外する。
探索半径は従来の 2 セルを保持し、距離が同じ場合の選択順序も維持する。各 Z 面・Y 行で固定のハッシュ値とラップ座標は内側のループで再利用する。
画像へのベイク、UV の量子化、オクターブ数の削減は行わず、拡大時にも元の式で値を求める。

`powershell -File scripts/test-noise-voronoi.ps1` は、実シェーダーの関数を抽出し、CPU の全探索と 10 万点で完全一致すること、不要な特徴点計算が減ることを確認する。
負座標、セル境界、大きな座標、周期 0 / 1 / 2 / 7 / 64 を含む。
実 GPU の確認は `powershell -File scripts/test-procedural-gpu.ps1 -VoronoiParity`（54 種類の画像出力と画素未満の UV におけるマテリアルの色・高さ・法線）。

単体計測は `powershell -File scripts/test-procedural-gpu.ps1 -NoiseBenchmark`。
RTX 3050 Laptop GPU、1024×1024、Voronoi / Hybrid Multifractal / 4 オクターブの高さ生成では、変更前約 32.5 ms、変更後約 6.9 ms（初回を除く 8 回平均、送信・フェンス待ち込み）。
これはノイズ生成単体の比較であり、POM・反射・画面内面積などを含むシーン全体の FPS は別途確認が必要。

CPU 回帰テスト: `python scripts/test-noise-materials.py`（C++20 コンパイラーが必要）。Windows の定義テスト: `powershell -File scripts/test-noise-assets.ps1`。

シェーダーのコンパイル: `python scripts/test-noise-shaders.py`（`DXC` にコンパイラーのパスを設定）。Windows の実 GPU / WARP 比較: `powershell -File scripts/test-procedural-gpu.ps1 -Warp`。この比較には全基底の細かい UV 位置での色・高さ・法線の CPU/GPU 比較を含む。

Linux で行った CPU テスト・DXC 検証は、Windows のアプリ全体のビルドや実機のドラッグ＆ドロップ・描画確認を代替しない。


### ベースカラーの適応 UV タイルキャッシュ

ベースカラーの計算結果を16×16頂点のUVタイルに保持し、画面上のUV変化量から格子の間隔を選ぶ。格子間隔は各UV軸のフットプリント以下。接近して1画素が覆うUV領域が小さくなれば、より細かいタイルを要求する。固定UV解像度の画像へ置き換えたり、ノイズのオクターブを減らしたりはしない。

タイル内は双線形補間し、RGBはFP16で保持する。そのため、元の式を全画素で評価した結果との完全一致ではない。未生成・追い出し・不正/極端なフットプリントの場合は元の式で描画し、その間に必要なタイルを生成する。ノイズの設定・色・シードを含む定義の指紋と、格子の細かさ・タイル座標をキーにするため、変更前の色を流用しない。負UVとタイル境界の床除算は整数で正確に扱う。

共通メモリは約67MiB（32,768ページ、タイルとメタデータ約65MiB、要求2MiB）。1ページは15×15セルと共有境界の頂点を持ち、境界を跨ぐ補間で隣のページを参照しない。4-way方式で空き/古いページを再利用する。描画中は完成済みキャッシュだけを読み、ミス時はバケットごとのatomicの勝者が定義208バイトとキーを要求へ書く。フレーム末尾のcomputeは1グループが1バケットを担当し、256頂点を元のScalar/Color関数で生成する。読み書きはリソース遷移/UAVバリアで分離し、スピン待ち・CPU読み戻し・描画中のレコード書き換えは行わない。

通常のラスタライズはUV微分、Visibility Resolveは再構成したUV微分を使用する。反射は追跡解像度と三角形のUV軸を分けてフットプリントを推定する。ガラスとGIカードも、それぞれの描画/キャプチャの広さから推定する。生成要求は主画面の描画に限定し、反射・GI・ガラスは既存タイルの読み取りだけを行う。疎な二次レイのために256頂点を新規生成する負荷を避け、二次レイのミス時は元の式に戻る。信頼できる微分を得られなければ元の式で描画する。法線・高さ/POM・画像生成の式は変更しない。

メインルートはSRV/UAVを1つのテーブルにまとめて64DWORD以内に収め、専用space15へバインドする。未確保時にも小さな有効バッファを用意し、無効ヘッダーにより通常計算へ戻す。GPU仮想アドレス0へのatomicは行わない。ノイズを使わないフレームの更新は省き、確保済みメモリは終了まで再利用する。`DX12_NOISE_CACHE=0` を起動前に設定すると比較用に無効化できる。

検証コマンド: `powershell -File scripts/test-procedural-gpu.ps1 -NoiseCache`。22基底、負UV/境界、16K画像の1画素より細かいUV、補間、細かい格子への切替、シード/色編集、競合・追い出し、未確保フォールバックを実GPUで確認する。単体測定の時間をシーン全体のFPSへ換算しない。カメラ移動・ジッター・初回生成の負荷も実シーンで比較する必要がある。

経緯: 完全に同じUVビットをキーにする先行方式は、移動する検証シーンでGPU4.91ms→5.11msとなり採用を取りやめた。適応タイル方式はUVが小さく動いても同じタイルを再利用できる。

既存の画像生成全体テストはWhite Noise（basis=4/fractal=0）で最大誤差0.737312により失敗する。変更前のProceduralTexture.hlsliと同じ既存noise.hlslでも同じ失敗を再現した。キャッシュのGPU検証・定義テスト・対象シェーダーのコンパイルと分けて扱う。


全体ビルド: Release/x64。GPUテストはRTX3050Laptopで、通常約14.0ms、再利用約1.24ms、細かなUV移動では約10.8ms→1.27ms（65536要求の混合基底単体、シーンFPSではない）。実シーンの対象解像度はユーザー指定に合わせ約250p（448×252）。`DX12_RENDER_BENCHMARK=1` と `DX12_RENDER_BENCHMARK_250P=1` でその診断モードを使用できる。通常起動時の保存設定は変更しない。


最終の受け入れ基準はユーザー指定の「約250p、60fps超」。448×252、出力1280×720、DXR/NRD有効、移動カメラ/TAA、120フレームの準備後240フレームでVoronoi4オクターブを比較し、無効約126fps→有効約137fps。タイル更新のGPU時間は約0.064ms。これは検証コピーのシーンでの測定で、あらゆる設定の最低FPSを保証するものではない。


重い実ファイル（Simplex / Domain Warp /10オクターブ）も同じ約250p・DXR/NRD・移動/TAA条件で確認し、キャッシュ有効時に平均119.6fps、1%低位63.6fps。Voronoiは平均137.1fps、1%低位68.4fps。ユーザーの60fps超という基準を確認したため、重いファイルの無効側の追加測定は途中で打ち切った。瞬間的な最低FPSや全設定を保証する数値ではない。

最終証拠は `build/noise-cache-validation/summary.json`、各ケースのframes/passes CSV、最終画像、使用定義、GPUテストとReleaseビルドのログ。Voronoi有効/無効で保存設定・カメラ再生・解像度が同一であることを確認した。通常のユーザーシーン・マテリアルを保存変更せず、検証コピーだけで定義を差し替えた。
